SharePoint MCP — Codebase Review

An MCP server that exposes a SharePoint Online tenant to LLM clients over stdio. It is a thin, uniform layer of Microsoft Graph wrappers, with one deliberate exception: modern-page authoring drops to the SharePoint REST API because Graph cannot create the web parts that matter.

Stack. Node 22+ / TypeScript (ESM), @modelcontextprotocol/sdk over StdioServerTransport, @microsoft/microsoft-graph-client, @azure/msal-node for auth, zod for input schemas. Builds with tsc to dist/. No runtime framework beyond the SDK.

TL;DR

Clean, consistent, easy to extend — every tool follows the same registerTool → wrapTool → graphClient shape. The standout engineering is in pages.ts, which works around a hard Graph limitation via SharePoint REST CanvasContent1 and seeds web-part properties from the live site manifest. Main gaps: no automated tests and reliance on Graph beta endpoints in a few tools.

Architecture

A single stdio process. index.ts boots the MCP server and registers nine tool modules. Most tools call Microsoft Graph through one shared client; page authoring takes a second path to the SharePoint REST API. Both paths get their tokens from the same MSAL-backed auth module.

Request flow. Two backends, one auth module. The accent path is the page-authoring workaround.

Key files

The tool pattern (util.ts + every module)

One shape repeats across all 80+ tools: a zod input schema, a handler wrapped by wrapTool, a Graph call, and a JSON result. Errors are normalized once.

src/util.tsTypeScript
export function wrapTool(handler) {
  return async (args) => {
    try { return await handler(args); }
    catch (err) {
      // GraphError → "status | code | message | requestId"; else generic
      return { content: [{ type: "text", text: formatGraphError(err) }], isError: true };
    }
  };
}

The payoff is uniformity: adding a tool means writing a schema and one Graph line. The cost is that there's no shared retry, throttling (HTTP 429) handling, or pagination — each tool returns the first page Graph gives it.

Auth (auth.ts)

Two modes, chosen by whether AZURE_CLIENT_SECRET is set: delegated device-code (token cached to %APPDATA%\sharepoint-mcp\token-cache.json, refreshed silently) or app-only client credentials. A separate getSharePointToken(hostname) mints a SharePoint-resource token for the REST page path.

Page authoring — the interesting part

Graph's Pages API can create text and simple web parts, but it rejects any web part whose properties contains an array of objects — Quick Links being the canonical case. The OData reader fails it regardless of payload shape (no annotation → "resource set without entity set"; Edm.Untyped → a server-side null reference). This is a Graph limitation, not a payload bug.

pages.ts sidesteps it by building the page's CanvasContent1 string and posting through the SharePoint REST pages API, then seeding each web part's default properties from the site's live manifest.

Strengths

Uniform, low-friction pattern

Every tool is schema + wrapTool + one Graph call. Predictable to read, trivial to extend, hard to get subtly wrong.

Centralized error shaping

formatGraphError surfaces status, code, and requestId — exactly what you need to debug Graph 4xx, returned as isError tool results rather than crashes.

Pragmatic dual backend

Graph where it works; SharePoint REST where it must. The page-authoring path solves a real problem most SharePoint tooling punts on.

Sensible auth + docs

Delegated and app-only modes with token caching, plus a real README, SETUP.md, and a live end-to-end smoke script.

Concerns

Warning

No automated tests

repo-wide · only scripts/verify-e2e.mts (needs a live tenant)

~2,876 lines with zero unit coverage. buildCanvasContent1 is a pure function ripe for testing without any network — regressions in canvas shaping would currently go unnoticed until a live run.

Warning

Reliance on Graph beta endpoints

sites.ts:337 (create_site) · sites.ts:357,376,395 (recycle bin)

Five tools call .version("beta"). Beta is explicitly unstable and can change or break without notice; these tools may silently regress against a tenant.

Info

No throttling / pagination handling

util.ts (no retry) · all list_* tools return res.value

Graph 429s aren't retried with Retry-After, and list tools return only the first page (no @odata.nextLink follow). Fine for interactive use; surprising at scale.

Info

Per-call web resolution; unbounded manifest cache

pages.ts — resolveWeb() & getManifests()

Each page op makes an extra Graph call to resolve webUrl. The manifest cache is a process-lifetime Map with no TTL — correct, but won't pick up tenant changes without a restart.

Info

Image web part is external-URL only

pages.ts — image case

Site-hosted images need siteId/webId/listId/uniqueId metadata; the typed image kind is best-effort for external URLs. Documented, but a sharp edge — library images must go through the standard kind.

Info

No LICENSE file

repo root · package.json declares ISC

ISC is declared in package.json and the README, but there's no LICENSE file — worth adding before the repo gets traction.

Recommendations

  • Add unit tests for buildCanvasContent1. Pure input → JSON string; highest value, zero infrastructure. Lock in the button-serverProcessedContent and Quick Links shapes so they can't silently regress.
  • Guard the beta endpoints. Either document them as unstable in the tool descriptions or gate them behind a flag, so a beta change doesn't quietly break create_site / recycle-bin tools.
  • Add 429 retry + optional pagination. A small wrapper in graph.ts for Retry-After, and a followNextLink option on list tools, would harden it for larger tenants.
  • Cache resolveWeb per site. Same memoization pattern already used for manifests; removes one Graph round-trip per page op.
  • Add a LICENSE file matching the declared ISC.
  • Consider PnPjs if page scope grows. It uses this same REST + CanvasContent1 approach but maintains web-part builders, section handling, and checkout for you — a natural migration if authoring features expand.
Bottom line

A focused, well-factored MCP server that does the boring parts cleanly and the hard part (native page web parts) genuinely well. The remaining gaps are about hardening — tests, beta exposure, throttling — not architecture.
